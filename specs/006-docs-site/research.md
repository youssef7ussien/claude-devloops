# Research: Documentation Site

Decisions for [plan.md](./plan.md). Each is Decision / Rationale / Alternatives. Facts about the
repository were read at `91fa92d` (before spec 005's last two commits, which removed the summary
page and the `dashboard.*` settings; re-checked when the reference pages are generated); facts about Zensical
were checked on 2026-10-10 against zensical.org/docs, PyPI, and the `zensical/zensical` source.

## R-1 Site builder: Zensical, pinned, configured in `zensical.toml`

- **Decision**: Zensical `0.0.69` (latest on PyPI, 2026-10-08), pinned exactly in
  `tools/docs/requirements.txt`. Native `zensical.toml` at the repository root, `docs_dir = "docs"`,
  output `site/` (ignored by git).
- **Rationale**: the developer's choice (spec Assumptions). Material for MkDocs, its predecessor,
  gets only critical fixes until 2026-11-05, and MkDocs itself has been unmaintained since
  2024-08. Zensical is pre-1.0 and releases every few days, so an exact pin and deliberate
  upgrades are needed (spec FR-004). `zensical.toml` is the format its own `zensical new` writes;
  `mkdocs.yml` would only matter for moving back to Material.
- **Alternatives**: Material for MkDocs (end of support next month); Starlight, VitePress,
  Docusaurus (a Node build for a Python repository); Sphinx (heavier, made for API references).

## R-2 Strict builds and link checks come from Zensical

- **Decision**: build with `zensical build --strict --clean`. Its validation of internal links and
  of link anchors is on by default; strict mode turns every warning into exit code 1.
- **Rationale**: FR-002 and SC-005 (0 broken links) without a link checker of our own. Anchor
  checks also cover links into the reference pages (R-7), which is how config keys, commands and
  statuses are checked in prose.
- **Alternatives**: our own link checker (duplicate work); lychee (external links only matter for
  a few GitHub links; not checked, recorded as a limitation).
- **Note**: Zensical is replacing its validation engine; an upgrade (R-1) re-runs the strict build
  before it is merged.

## R-3 Markdown features: the default set plus snippets

- **Decision**: list `markdown_extensions` explicitly: Zensical's default set (admonition,
  attr_list, def_list, details, footnotes, md_in_html, toc with permalinks, highlight,
  inlinehilite, superfences with the `mermaid` fence, tabbed, tasklist, abbr, keys, mark, tilde)
  plus `pymdownx.snippets` with `base_path = ["docs-include"]` and
  `auto_append = ["abbreviations.md"]` (relative to `base_path`).
- **Rationale**: setting `markdown_extensions` replaces the whole default list, so it must be
  re-listed. Snippets let pages include generated example outputs (R-9) and append the glossary's
  abbreviations, which show as hover definitions of terms (FR-015). Snippet files live outside
  `docs/`, as Zensical advises, so they do not warn as unreferenced pages.
- **Alternatives**: inline examples copied into pages (would drift; FR-019 forbids typing them).

## R-4 Page sources in front matter, not HTML comments

- **Decision**: each hand-written page starts with front matter:
  `sources: [loops/shared/devloops/engine.py, "spec 001 FR-012", …]`.
- **Rationale**: FR-020 asks for the list to stay out of the rendered page. Python-Markdown passes
  HTML comments into the HTML; front matter never reaches the output. A test can read it (R-8).
- **Alternatives**: an HTML comment (ends up in the HTML); a separate index file (drifts from the
  pages).

## R-5 Reference pages: what comes from where

The reference pages are generated by `tools/docs/gen_reference.py` (standard library only, imports
devloops from `loops/shared`). What the code already holds is read from it; what it does not hold
(the meaning of an exit code, a status, a step) is kept in one descriptions file, and a test makes
the two agree.

| Page | Read from the code | Descriptions from |
|------|--------------------|-------------------|
| Commands | `cli.build_parser()` (cli.py:103): commands, options, mutually exclusive groups, help text; suppressed options left out; `REMOVED_DASHBOARD_FLAGS` (cli.py:39) as a "removed options" table | argparse `help=` |
| Configuration | `config.schema.json`, `project-config.schema.json`: keys, types, enums, defaults; merge order from `config.load_effective` (config.py:1-3, 78) | schema `description` (R-6) |
| Exit codes | `state.EXIT_CODES`, `EXIT_USAGE`, `EXIT_LOCK_HELD` (state.py:12-20), and the codes set by error classes | `tools/docs/descriptions.json` |
| Steps | `claude.STEPS` (claude.py:74): order, writes, tools, output schema | `descriptions.json` |
| Statuses | loop `status` and `status_reason.code` enums (run-state.schema.json); run, milestone, task, trial, approval values | `descriptions.json` |
| State files | the files a sample run writes (R-9) and the schemas of `run.json`, `plan.json`, invocation records, validation results, checks | schema `description`s, `descriptions.json` for files without a schema |

- **Rationale**: FR-017 needs the keys from the code so nothing is missed; prose meanings have no
  home in the code today. One descriptions file keyed by value, with a test that every value in
  the code has a description and every description has a value (R-8), keeps them in step without
  adding prose to the code.
- **Statuses without a schema enum** (run status in `run/state.json`; milestone, task and trial
  statuses, which the schema names only in prose): the generator takes their values from small
  module constants added for this purpose (`state.RUN_STATUSES`, `MILESTONE_STATUSES`,
  `TRIAL_STATUSES`, `TASK_STATUSES`), which the engine and orchestrator then use instead of string
  literals. A test checks that no other status string is written.
- **Found while researching**: the manual says exit code 30 means "invalid project configuration",
  but an invalid run configuration (`config.schema.json`) exits 2 (`ConfigError` is a
  `UsageError`, config.py:17). The generated page states what the code does; whether 2 is right
  is recorded as a follow-up, not changed here (spec: out of scope).
- **Alternatives**: hand-written reference tables (what the manual has now; nothing catches
  drift); descriptions as code docstrings or constants (moves documentation prose into the
  driver, against the "write it once, in the docs" aim).

## R-6 Missing configuration descriptions are added to the schemas

- **Decision**: add a `description` to every configuration key that lacks one in
  `config.schema.json` and `project-config.schema.json` (the agent found 18 present and about 25
  missing, e.g. `invocation_timeout_seconds`, `models.*`, `runtime.*`, `secrets.*`), and to their
  byte-identical copies in `specs/001-reusable-dev-loops/contracts/` and
  `specs/002-devloops-init/contracts/` (test_schemas_sync).
- **Rationale**: the schema already is where 18 keys are described; splitting descriptions between
  the schema and a docs file would leave two places to look. A description changes no
  validation.
- **Alternatives**: config descriptions in `descriptions.json` (two sources for one kind of fact).

## R-7 Checking the hand-written pages

- **Decision**:
  - **Links**: the strict build (R-2).
  - **Config keys, commands, statuses, steps, exit codes in prose**: the writing style requires
    linking a mention to its reference entry (e.g. `[max_trials](../reference/configuration.md#max_trials)`),
    so the strict build's anchor check catches a key that no longer exists.
  - **Configuration keys in inline code**: a dotted name (`unit_tests.command`) or a word equal to
    a top-level key name must be a key of the schemas, so an unlinked mention is checked too
    (FR-018).
  - **Commands in examples**: `test_docs` reads every line in code blocks and inline code that
    starts with `devloops ` and checks the command and each `--option` against
    `cli.build_parser()`.
  - **Workspace paths**: inline code that looks like a workspace path (`state/…`, `outputs/…`,
    `run/…`, with `<id>`, `<n>`, `<seq>` as wildcards) must match a file the sample run writes
    (R-9).
- **Rationale**: FR-018 with the least machinery: the build already checks anchors, so linking
  turns most checks into link checks; only commands and paths need code.
- **Alternatives**: scanning prose for every word that might be a key (false matches).

## R-8 The docs tests

- **Decision**: `loops/shared/tests/test_docs.py`, run with the rest of the suite:
  1. each generated reference page equals what `gen_reference.py` produces now (FR-017);
  2. `descriptions.json` and the code have the same values (R-5);
  3. every hand-written page has front matter with a non-empty `sources`, and every file it names
     exists and every requirement ID it names exists in `specs/` (FR-020);
  4. commands and paths in pages (R-7);
  5. every status of each kind appears in its diagram on the statuses page (FR-008);
  6. the example outputs equal what `examples.py` produces now, after normalising paths and times
     (FR-019);
  7. `zensical build --strict` succeeds, when Zensical is installed (skipped otherwise, as the node
     tests are without node).
- **Rationale**: the same pattern as `test_schemas_sync` and `test_app_js`: drift fails the suite
  and names the page.

## R-9 Examples from a real run

- **Decision**: `tools/docs/examples.py` reuses the test helpers (`helpers.TempEnv`,
  `write_scenario`, `run_cli`, `samples.plan()`; the backend loop's `fixtures/http_app.py` as the
  sample application) to run `init`, `check`, `run`, `approve`, `status` and `dashboard --export`
  against the stand-in Claude Code, writes each command's output to
  `docs-include/examples/<name>.txt` with temporary paths, times and durations replaced by fixed
  placeholders, and lists the files the run wrote (`docs-include/examples/workspace-files.txt`,
  used by R-7).
- **Rationale**: FR-019; the helpers already build exactly this kind of run for the tests.
- **Note**: the sample application and plan are generic (no application specifics,
  constitution II).

## R-10 Screenshots

- **Decision**: `tools/docs/screenshots.mjs` (Node, as the dashboard's browser tests; drives
  headless Chromium over the DevTools protocol) opens the dashboard of the sample workspace from
  R-9 and saves one PNG per view, light theme, 1400×900, into `docs/assets/screenshots/`. Run by
  hand when the dashboard changes; not part of the test suite.
- **Rationale**: FR-010 and FR-019 (from a real run); a browser is not available in every test
  run.
- **Alternatives**: screenshots of a developer's own project (not reproducible, may show
  application specifics); Playwright as a dependency (Chromium over CDP is already how the
  dashboard was checked during spec 005).

## R-11 Publishing

- **Decision**: `.github/workflows/docs.yml`: on pushes to `main` that touch `docs/`,
  `docs-include/`, `tools/docs/`, `zensical.toml`, `loops/` or the workflow, and on pull requests
  (build only, no deploy):
  `actions/checkout@v7`, `actions/setup-python@v7` (Python 3.12), `pip install -r
  tools/docs/requirements.txt`, run `test_docs`, `zensical build --strict --clean`; on `main`,
  `actions/configure-pages@v6`, `actions/upload-pages-artifact@v5` (`site/`),
  `actions/deploy-pages@v5`. No caching (Zensical advises against it for now).
- **Rationale**: FR-001, FR-002, SC-006; the official Zensical workflow plus the docs tests. The
  repository is public, so Pages is free; the owner switches Pages on once (Settings → Pages →
  Source: GitHub Actions).
- **Note**: this is the repository's first CI workflow. It runs only the docs tests, not the full
  suite (about 10 minutes, and needs `claude`-free fakes only; a full CI is a separate decision).
- **Zensical needs Python ≥ 3.11**; devloops supports 3.10. The docs build runs in CI and on
  developers' machines only, so devloops' own requirement does not change.

## R-12 Page layout and navigation

- **Decision**: top-level tabs: Home, Getting started, How it works, Guides, Reference,
  Contributing. Pages:
  - `index.md` (landing);
  - `getting-started/` (`install.md`, `first-run.md`);
  - `how-it-works/` (`index.md` overview, `run-lifecycle.md`, `steps.md`, `validation.md`,
    `trials-and-recovery.md`, `statuses.md`, `state-and-files.md`, `dashboard-data.md`);
  - `guides/` (`backend-loop.md`, `frontend-loop.md`, `dashboard.md`, `approval-and-questions.md`,
    `configuration.md`, `prompts.md`, `spec-kit.md`, `skills.md`, `security.md`, `upgrades.md`,
    `limitations.md`);
  - `reference/` (generated: `commands.md`, `configuration.md`, `exit-codes.md`, `steps.md`,
    `statuses.md`, `state-files.md`);
  - `glossary.md`;
  - `contributing/` (`index.md`, `architecture.md`, `testing.md`, `specs-process.md`,
    `writing-style.md`, `documentation.md`).
- **Rationale**: FR-005's sections; a reader new to devloops moves Home → Getting started → How it
  works; guides answer "how do I…"; reference answers "what exactly…". Generated pages stay in one
  folder so nobody edits them by mistake (each starts with a "generated, do not edit" note).
- **Manual coverage** (FR-022, SC-008): `manual-map.md` in this spec folder maps every heading of
  `loops/README.md` (and `loops/orchestrator/README.md`) to its new page, or to "dropped" with the
  reason.

## R-13 Root README, package description, and pointers

- **Decision**: a root `README.md` of about 80–120 lines (what devloops is, the core idea, a
  quick start, links to the site's sections); `pyproject.toml` `readme = "README.md"`;
  `loops/shared/skills/devloops-run/SKILL.md` links the recovery page by its site address;
  `bin/devloops` and `initcmd.py:148` cite the site; `CLAUDE.md` names `docs/` as the user
  documentation and moves the "Changed by spec NNN" and "describe the system as built" rules to
  it; `test_no_app_specifics` excludes `docs/` and `docs-include/` as it excluded the manual.
  `loops/orchestrator/README.md` is folded into the site too.
- **Rationale**: FR-023, FR-024; `loops/README.md` is removed (FR-022).

## R-14 Reviews and readers

- **Decision**: each hand-written page is reviewed against its `sources` by a separate agent
  before its first merge, which lists every statement it could not confirm; the writer fixes or
  removes them (FR-021). SC-001 and SC-003 are checked with two readers who have not used devloops,
  named by the developer, after the landing page and "How it works" are written.
- **Rationale**: the independent check the developer agreed; readers are people, so the plan names
  the step and the developer names the people.
