# Documentation

This site is devloops' user documentation. Its pages are Markdown files in `docs/`, built
into a website by [Zensical](https://zensical.org/) with the settings in `zensical.toml`, and
published to GitHub Pages by `.github/workflows/docs.yml`.

## The rule: pages describe devloops as it is

The constitution requires documentation to reflect the system as built, not as planned. So a
change in behavior updates the pages that describe it **in the same commit**, never later.
Pages say what devloops does today.

When a later spec changes behavior an earlier spec described, the earlier spec gets a
"Changed by / Revised by spec NNN" note in place. The site's pages that describe the behavior
are rewritten to the new behavior, and get a short note of the same kind where the change is,
naming the spec (spec 006 FR-025). The note says what changed; the page around it describes
only the current behavior (see
[specs process](specs-process.md#when-a-later-spec-changes-earlier-behavior)).

How to write a page, and the rules every page follows, are in
[writing style](writing-style.md).

## What is written by hand, and what is generated

| Folder | What it holds | How it changes |
|---|---|---|
| `docs/` (except `docs/reference/`, but including `reference/index.md`) | The hand-written pages | Edit them |
| `docs/reference/` | The reference pages: commands, configuration keys, exit codes, steps, statuses, state files | Generated by `tools/docs/gen_reference.py`; never edit them |
| `docs-include/examples/` | Every command output the pages show | Generated by `tools/docs/examples.py`; never edit them |
| `docs-include/abbreviations.md` | The glossary's hover definitions | Edit it with the [glossary](../glossary.md) |
| `docs/assets/screenshots/` | The dashboard screenshots | Taken by `tools/docs/screenshots.mjs`, by hand |

### The reference pages

`gen_reference.py` reads devloops itself: the commands and options from `cli.build_parser()`,
the settings from the two configuration schemas, the exit codes, the steps from
`claude.STEPS`, the statuses from the constants in `state.py` and the schema enums, and the
files a run writes from the sample run's file list. What the code does not hold, the meaning
of an exit code, a step, a status or a file, is in `tools/docs/descriptions.json`.

To change what a reference page says, change its source, then regenerate:

- a command or option: its `help=` text in `cli.py`;
- a configuration key: its `description` in `loops/shared/schemas/` (and the copy in the spec's
  `contracts/`, which must stay identical);
- an exit code, step, status, stop reason or file: its entry in `descriptions.json`.

```sh
python3 tools/docs/gen_reference.py
```

### The example outputs

`examples.py` runs devloops for real against the [stand-in](../glossary.md#stand-in) Claude
Code the tests use, on a small
generic application (an items service), and writes each command's output to
`docs-include/examples/<name>.txt`, plus the list of files the run wrote. Paths, times,
durations, ports and ids are made the same on every machine, so the files change only when
devloops' output does. Pages include them with a snippet (see
[writing style](writing-style.md#examples)).

```sh
python3 tools/docs/examples.py          # rewrite docs-include/examples/
python3 tools/docs/examples.py --keep   # write nothing; keep the sample project, print its path
```

After a change to what a command prints, run it and commit the new outputs with the change.
Then regenerate the reference too: its list of state files comes from the sample run.

### The screenshots

The dashboard screenshots are retaken by hand when the dashboard changes, not by the tests (a
browser is not always there):

```sh
node tools/docs/screenshots.mjs
```

It runs the same sample (`examples.py --keep`), starts the project's dashboard in the
background, opens it in headless Chromium at 1400×900 in the light theme, and writes one PNG
per view to `docs/assets/screenshots/`. It needs Node 22 or later and Chromium or Chrome (set
`CHROME` to its path if it is not found). Look at the new images before committing them.

## The checks

`loops/shared/tests/test_docs.py` is part of devloops' test suite. Its checks:

1. The reference pages are current: `gen_reference.py --check` writes nothing and names each
   page that differs.
2. `descriptions.json` describes exactly the values the code has: it names each value with no
   description, and each description of a value that no longer exists.
3. Every hand-written page has a `title`, a `description` and `sources`, and each source exists
   (a path in the repository, or a requirement ID found in its spec).
4. Every command, option, configuration key and workspace path a page shows in code exists in
   devloops.
5. Every status of each kind appears in its diagram on
   [statuses](../how-it-works/statuses.md).
6. The example outputs are current: `examples.py --check` names each file that differs.
7. The site builds with `zensical build --strict --clean`. This check is skipped when Zensical
   is not installed; the workflow always runs it.

Each failure names the page, the line when there is one, and the item, for example:

```text
docs/guides/configuration.md:42: 'unit_tests.enable' is not a configuration key
```

Run them alone with:

```sh
cd loops/shared/tests && VISUAL=true EDITOR=true python3 -m unittest test_docs
```

The strict build is the link check. Zensical checks every link between pages and every anchor
in them, and `--strict` turns any warning into a failure: a link to a reference entry that was
renamed, or to a page that was moved, fails the build and names the page. A snippet that names
a missing file fails it too.

## Previewing a change

Zensical is a tool for writers and for the workflow, not something devloops needs to run. It
is installed in its own virtual environment:

```sh
python3 -m venv .venv-docs && .venv-docs/bin/pip install -r tools/docs/requirements.txt  # once
.venv-docs/bin/zensical serve                    # preview at http://localhost:8000, reloads on save
.venv-docs/bin/zensical build --strict --clean   # the build the workflow runs, into site/
```

`site/` and `.venv-docs/` are ignored by git.

## Review before a page is first published

A new page, or a rewritten one, is checked against its sources by a reviewer who did not write
it, before it is first published. The reviewer reads the page beside every file and
requirement in its `sources`, and lists:

- every statement the sources do not confirm;
- every devloops word neither explained where it is first used nor linked to the glossary;
- anything that describes planned or removed behavior as if it were current.

The writer fixes or removes each one. The tests catch names that do not exist; only a reader
catches a sentence that is wrong.

## Publishing

On every push to `main`, and every pull request, that touches `docs/`, `docs-include/`, `tools/docs/`,
`zensical.toml`, `loops/` or the workflow itself, the workflow runs `test_docs` and the strict
build with Python 3.12. On a push to `main`, it then publishes the built site to GitHub Pages.
The repository's Pages setting must be set to deploy from GitHub Actions.

## Upgrading Zensical

Zensical is young and releases often, so its version is pinned exactly in
`tools/docs/requirements.txt`, and it changes only on purpose, in a commit of its own:

1. Read the release notes since the pinned version.
2. Change the pin, and reinstall it in `.venv-docs`.
3. Run the strict build and `test_docs`, and look through the site with `zensical serve`:
   the home page, a diagram, the search, the dark theme, and a page at phone width.
4. Commit the new pin, with any change to `zensical.toml` it needs.
